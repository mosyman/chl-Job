其中几个点，面试和实际工作中尤其容易混淆：

- **Admission control 与调度不同**：前者决定请求是否进入、何时准入；后者决定已接纳请求如何获得执行资源。单纯限制请求数，通常不足以反映不同长度请求的成本。
- **Prefix reuse 主要减少重复 prefill**，不能直接省掉每个新 token 的 decode。缓存键还需考虑前缀依赖、模型/权重版本、LoRA、多模态内容与隔离条件。[vLLM Prefix Cache 设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)
- **Prefill 常偏计算瓶颈，低批量 decode 常偏带宽瓶颈**，但实际瓶颈会随 batch、上下文长度、模型和硬件改变，必须测量。
- **推测解码不保证所有负载都加速**。接受率、草稿成本、验证成本和并发都会影响收益；严格保持目标采样分布还需要正确的接受与拒绝后重采样过程。[Speculative Decoding 原始论文](https://proceedings.mlr.press/v202/leviathan23a.html)
- **PD 分离需要支付 KV 传输成本**，应联合考虑网络、缓存命中、P/D 配比和独立扩缩容。[TensorRT-LLM PD 设计](https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/features/disagg-serving.md)
- **GPU utilization 高不等于系统效率高**。可能仍有冗余计算、低效 kernel、尾延迟恶化或单位 token 成本过高。

性能指标至少要能解释和测量下表这些。

| 指标 | 含义与注意事项 |
|---|---|
| **TTFT** | 首 token 延迟；客户端口径通常包含网络、排队、预处理和 prefill |
| **ITL / TBT** | 相邻输出 token 的时间间隔；流式响应可能一次包含多个 token，测量口径需要明确 |
| **TPOT** | 每个输出 token 的平均生成耗时；常用估算为 `(总延迟−TTFT)/(输出 token 数−1)`，适用于输出超过一个 token |
| **E2E latency** | 整个请求从开始到完成的耗时 |
| **Throughput** | 请求/秒、输入 token/秒、输出 token/秒；必须标明统计对象 |
| **Goodput** | 满足指定延迟等 SLO 的有效吞吐 |
| **P50/P95/P99** | 延迟分布，尤其关注高负载下的尾延迟 |
| **缓存与资源指标** | 命中请求比例、命中 token 比例、KV 占用、抢占率、重计算量、队列深度、传输量 |
| **稳定性与成本** | 错误率、拒绝率、超时率、OOM、恢复时间，以及给定工作负载和 SLO 下的单位 token 成本 |

实际压测应固定模型、硬件、精度、输入/输出长度分布、采样参数及缓存冷热状态，并区分固定并发与固定到达速率的实验。[GuideLLM 官方说明](https://github.com/vllm-project/guidellm)

KV Cache 容量估算也是基本功。对于常规、各层配置相同的 MHA/GQA 模型，未考虑共享、分片和额外开销时：

\[
M_{\mathrm{KV}}\approx 2\times L\times H_{\mathrm{KV}}\times D_{\mathrm{head}}
\times \text{每元素字节数}\times \sum_i T_i
\]

例如 32 层、8 个 KV heads、head dimension 为 128、BF16，KV 约为 **128 KiB/token**，一个 8192-token 序列约占 **1 GiB**。真实部署还需考虑块取整、共享、TP 下的分片或复制；MLA、滑窗和混合架构需另算。

### 3. Decoding 优化

- **投机解码原理**：小模型先起草、大模型再验证，用拒绝采样保证输出分布不变。设接受率为 α、草稿长度为 γ，每步期望产出 (1−α^(γ+1))/(1−α) 个 token。batch 越大收益越小，所以草稿长度要动态调整
- **方法**：独立草稿模型、Medusa、EAGLE-1/2/3/3.1、MTP（DeepSeek-V3 自带）、Lookahead（Jacobi 迭代）、n-gram 匹配、Suffix Decoding、P-EAGLE（一次前向生成多个草稿 token）、DFlash（块扩散方式生成草稿）
- **工程实现**：用树状 attention mask 一次验证多条候选、拒绝后回滚 KV、与 CUDA Graph 和 PD 分离结合、训练草稿模型
- **前缀复用与并行解码**：n>1 时多个样本共享 prompt 的 KV（写时复制）、beam search、GRPO 组采样共享前缀
- **结构化输出**：用 FSM/PDA 约束生成、缓存 token mask、jump-forward、把 mask 计算与 GPU 计算重叠
- **采样 kernel**：免排序的 top-k/top-p 实现、logits processor 带来的 CPU 开销

### 4. 推理执行引擎（执行图 / 算子调度 / runtime）

- **执行模型**：model runner、输入准备（CPU 端构造 attention metadata 是主要开销之一）、persistent batch、attention 后端抽象
- **图优化**：CUDA Graph（录制与重放、按 batch 分桶、分段录制）、torch.compile（自定义融合，例如 AllReduce 和 RMSNorm 融合）、把整个模型编译成一个 megakernel

### 5. GPU 利用率优化（kernel / IO / 调度瓶颈）

- **硬件**：SM 和 warp 层级、Tensor Core（Hopper 的 WGMMA、Blackwell 的 tcgen05）、HBM、L2、shared memory、TMA、异步拷贝
- **分析方法**：roofline 和算术强度。decode 阶段 GEMM 的算术强度大约等于 batch size；attention 主要受带宽限制，GQA/MLA 能提高它的算术强度。还要会看 MFU/MBU、occupancy、warp stall，用 Nsight Systems 找出 CPU 端的 kernel 启动间隙和同步点
- **kernel 技术**：tiling、online softmax、split-KV（FlashDecoding）、persistent kernel、warp specialization、FP8/FP4 分块缩放 GEMM、MoE grouped GEMM
- **编程工具**：CUDA C++、CUTLASS/CuTe DSL、Triton、TileLang、cuTile、ThunderKittens
- **系统层面**：用 CUDA Graph 消除 kernel 启动开销；在同一张卡上并行跑计算型、访存型和通信型 kernel（NanoFlow）；用 pinned memory 和 GPUDirect 提高 IO 带宽

### 6. 分布式推理 / 高并发在线服务

- **拆分部署**：PD 分离（prefill 和 decode 分开部署，涉及 KV 传输和 P/D 配比）、AF 分离（attention 和 FFN 分开部署）、多模态 encoder 单独部署
- **通信**：NCCL、NVSHMEM（在 kernel 内直接发起通信）、RDMA/UCX、自定义 all-reduce、计算与通信重叠
- **在线服务**：OpenAI 兼容 API、流式输出、按 KV 和 PD 角色路由、按 KV/队列指标扩缩容、LoRA 管理、容错、冷启动加速、K8s 编排、可观测性

### 7. 训练协同（RL rollout / 评测加速）

- **架构**：一种是训练和推理分时共用同一批 GPU，推理引擎在切换时释放显存；另一种是两者用各自的 GPU 池。RL 可以同步也可以异步，异步时要控制生成所用策略落后的程度，并做重要性采样修正
- **rollout 特性**：少数超长生成会拖住整批（长尾问题），对策有部分 rollout、中断后续跑；GRPO 组采样共享前缀；多轮 Agent rollout（工具调用、沙箱）
- **权重同步**：NCCL broadcast 并分桶、CUDA IPC、RDMA 点对点；训练端（FSDP/Megatron）和推理端（TP/EP）切分方式不同，需要重新切分；FP8 rollout
- **训推一致**：logprob 不一致的来源（归约顺序、TP 大小、batch 组成），以及确定性推理
- **评测加速**：离线批量推理（大 batch、DP、复用 few-shot 前缀缓存）

1. nano-vllm → mini-sglang

4. 用 Dynamo 或 llm-d 部署一套 PD 分离
5. 用 verl 或 slime 跑一次 GRPO，观察 rollout 的耗时瓶颈
