


# claude - Go 锁:从「为什么要」到「怎么用」到「底层原理」

## 0. 先搞清楚:锁是用来解决什么的?

多个 goroutine(Go 的轻量级线程)**同时读写同一块内存**,结果就会乱套。这叫 **data race(数据竞争)**。

最经典的例子——两个 goroutine 同时给 map 写入:

```
goroutine A                goroutine B
    |                          |
    |  读 map 内部结构 ----+    |  读 map 内部结构
    |                     |    |
    |  改写 bucket -------+----+--- 同时改写同一个 bucket
    |                          |
    v                          v
       map 内部结构被写坏 -> 程序 panic / 数据错乱
```

**图解说明**:map 不是一个「原子」操作,写入 map 内部要改好几处指针(bucket、count 等)。A 改到一半,B 也进来改,两者交错,map 的内部不变量(invariant)就被破坏了。
Go 的 map **故意**在运行时检测到并发写时直接 `panic: concurrent map writes`,而不是悄悄返回错误值——这是 Go 的设计哲学:并发 bug 要尽早暴露。

锁的作用就一句话:**保证「同一时刻只有一个 goroutine 能进入这段临界区(critical section)」**,其它 goroutine 排队等。

## 1. `sync.Mutex`:互斥锁(最基础)

### 1.1 语法解析

`Mutex` 来自标准库 `sync` 包,只有两个方法:

```go
var mu sync.Mutex   // 零值可用,不需要 new / 初始化
mu.Lock()           // 加锁:拿到锁才能往下走,拿不到就阻塞排队
// ... 临界区:这里的代码同一时刻只有一个 goroutine 在跑 ...
mu.Unlock()         // 解锁:释放,让排队的下一个进来
```

三个关键点,你作为小白一定要记住:

1. **零值可用**。`var mu sync.Mutex` 直接就能用,不需要 `mu = sync.Mutex{}` 或 `new`。这是 Go 标准库的常见设计。
2. **`Mutex` 不能被复制**。因为它内部存着锁的状态(见 §1.3),复制一份会把「已锁」状态也复制走,逻辑就错了。所以结构体里放 `Mutex` 时,方法接收者永远用**指针** `func (s *inMemoryAsyncJobStore)`,不是值 `func (s inMemoryAsyncJobStore)`。
3. **它保护的是「数据」,不是「代码」**。锁本身只是个标志位,它和它要保护的那个 map/变量之间的关联**全靠你自己约定**。约定俗成:把 `mu` 字段紧挨着它保护的字段放在一起。

### 1.2 仓库真实代码

看 [async_job_registry.go:538-549](pkg/plugins/gateway/async_job_registry.go#L538-L549) 的结构体定义:

```go
type inMemoryAsyncJobStore struct {
	mu      sync.RWMutex              // 这把锁,保护下面这个 records
	records map[string]AsyncJobRecord // 被保护的数据
	now     func() time.Time
}
```

> 注意它用的是 `RWMutex`(读写锁,§2 讲),但先把它当普通 `Mutex` 看,因为写操作的用法完全一样。

写入操作 [async_job_registry.go:555-563](pkg/plugins/gateway/async_job_registry.go#L555-L563):

```go
func (s *inMemoryAsyncJobStore) put(_ context.Context, record AsyncJobRecord) error {
	if err := record.validate(); err != nil {   // 校验放在加锁之前
		return err
	}
	s.mu.Lock()                                   // ← 加锁
	defer s.mu.Unlock()                           // ← defer 解锁
	s.records[inMemoryAsyncJobKey(record.Owner, record.PublicJobID)] = record
	return nil
}
```

删除操作 [async_job_registry.go:615-620](pkg/plugins/gateway/async_job_registry.go#L615-L620) 同样:

```go
func (s *inMemoryAsyncJobStore) delete(_ context.Context, owner, publicJobID string) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.records, inMemoryAsyncJobKey(owner, publicJobID))
	return nil
}
```

### 1.3 `defer Unlock` 这个惯用法为什么重要

```go
s.mu.Lock()
defer s.mu.Unlock()   // defer = 函数返回时才执行
// 临界区...
```

`defer` 的意思是「把这句推迟到当前函数 **return 的那一刻** 再执行」。为什么一定要配 `defer`?

对比不用 defer 的写法,一旦临界区里有多个 `return` 分支,或者中途 `panic`,你很容易**忘记解锁**:

```go
// ❌ 危险写法
s.mu.Lock()
if cond {
    return err      // 糟糕!这里直接返回了,锁没解,其它 goroutine 永远卡死
}
s.mu.Unlock()
```

锁没被释放,所有后续想拿这把锁的 goroutine 全部永久阻塞,这叫 **死锁(deadlock)**。`defer` 保证**无论从哪个分支返回、甚至 panic,解锁都一定会执行**。注意看仓库里这个例子——校验 `record.validate()` 故意放在 `Lock()` 之前([async_job_registry.go:556-558](pkg/plugins/gateway/async_job_registry.go#L556-L558)):能不进临界区就不进,临界区越短越好(锁的持有时间越短,并发度越高)。

### 1.4 底层原理

Go 源码 `src/sync/mutex.go` 里,`Mutex` 的结构体极其简单:

```go
type Mutex struct {
	state int32   // 用位运算打包了:是否已锁、是否有 goroutine 在等、是否饥饿模式
	sema  uint32  // 信号量,用来挂起/唤醒等待的 goroutine
}
```

工作流程(简化):

```
         Lock() 被调用
              |
              v
   +---------------------------+
   | 用 CAS 原子操作尝试把      |   CAS = Compare-And-Swap
   | state 从「未锁」改成「已锁」|   (硬件级原子指令,无需操作系统参与)
   +---------------------------+
        |                  |
    成功 |              失败(别人持有)
        |                  |
        v                  v
  直接进入临界区     自旋几次 (spin) 还抢不到
  (快路径,极快)          |
                          v
                   通过 sema 信号量把自己挂起,
                   让出 CPU,排进等待队列
                   (慢路径,涉及调度器)
                          |
            持锁者 Unlock() 时唤醒队首 ---+
```

**图解说明**:

- **快路径(fast path)**:没有竞争时,`Lock` 只是一条 CAS 原子指令,几纳秒,完全不进操作系统内核,极快。这是为什么 Go 的 Mutex 在低竞争下几乎零开销。
- **自旋(spinning)**:抢不到锁时,不是立刻睡觉,而是先空转几圈赌「持锁者马上就放」。因为「挂起 + 唤醒」要走调度器,代价比空转几纳秒高。
- **慢路径 + 饥饿模式(starvation mode)**:如果一个 goroutine 等太久(超过 1ms)还没拿到锁,Mutex 会切到「饥饿模式」——锁直接**手递手**交给等待队列的队首,防止某个倒霉蛋被后来者一直插队、永远饿死。这是 Go 1.9 加的公平性保证。

你不需要记住位运算细节,但要记住这个心智模型:**无竞争时锁几乎免费;有竞争时才会真正让出 CPU 去排队**。

## 2. `sync.RWMutex`:读写锁(读多写少时的优化)

### 2.1 为什么需要它

普通 `Mutex` 太「霸道」:哪怕 10 个 goroutine 只是**读**数据(互相之间根本不冲突),也只能一个一个排队。但现实中「读远多于写」太常见了(比如这个 job 注册表,`get` 调用频率远高于 `put`)。

`RWMutex` 的规则:

- **读锁(RLock)可以同时被多个 goroutine 持有** —— 读和读不冲突。
- **写锁(Lock)是独占的** —— 写的时候,其它读、写全部挡在门外。

```
场景:5 个读 goroutine + 1 个写 goroutine

时间轴 ---->

RLock:  R1 ===========
        R2 ===========      <- 读之间并行,全部同时进行
        R3 ===========
                      (读全部结束,写才能进)
Lock:                  W1 ==========   <- 写独占,此刻无人能读
                                 (写结束)
RLock:                            R4 ======  <- 又可以并行读了
                                  R5 ======
```

**图解说明**:`R1~R3` 并行执行,互不阻塞,这就是 RWMutex 相对 Mutex 的性能收益。但 `W1`(写)来的时候,它必须等所有在读的结束、且期间新来的读要排在它后面(防止写被源源不断的读「饿死」)。

### 2.2 语法解析

比 Mutex 多两个方法,共四个:

```go
var mu sync.RWMutex
mu.Lock()     / mu.Unlock()     // 写锁:独占
mu.RLock()    / mu.RUnlock()    // 读锁:共享

// ⚠️ 配对不能错:RLock 必须配 RUnlock,Lock 必须配 Unlock,不能交叉!
```

### 2.3 仓库真实代码:读路径用 RLock

回到同一个文件,`get` 操作 [async_job_registry.go:565-581](pkg/plugins/gateway/async_job_registry.go#L565-L581):

```go
func (s *inMemoryAsyncJobStore) get(_ context.Context, owner, publicJobID string) (AsyncJobRecord, error) {
	now := s.now()
	s.mu.RLock()                                            // ← 读锁
	record, ok := s.records[inMemoryAsyncJobKey(owner, publicJobID)]
	s.mu.RUnlock()                                          // ← 这里没用 defer!下面讲为什么
	if !ok {
		return AsyncJobRecord{}, fmt.Errorf("%w: %s", errAsyncJobNotFound, publicJobID)
	}
	if record.expired(now) {
		// 读的时候发现过期了,要删掉它 —— 需要升级成写锁
		s.mu.Lock()                                         // ← 写锁
		delete(s.records, inMemoryAsyncJobKey(owner, publicJobID))
		s.mu.Unlock()
		return AsyncJobRecord{}, fmt.Errorf("%w: %s", errAsyncJobNotFound, publicJobID)
	}
	return record, nil
}
```

### 2.4 ⚠️ 一个小白必踩的坑:锁不能「升级」

注意上面 `get` 为什么**故意不用 `defer s.mu.RUnlock()`**?

因为代码逻辑是:先读(RLock),发现过期后要删(需要 Lock)。而 Go 的 `RWMutex` **不支持把读锁直接升级成写锁**。如果你写成下面这样,会**立刻死锁**:

```go
// ❌ 死锁!
s.mu.RLock()
defer s.mu.RUnlock()           // 读锁要到函数结束才释放
// ...
s.mu.Lock()                    // 想拿写锁,但写锁要等所有读锁释放...
                               // 而这个读锁正是我自己持有的、要等函数结束才放
                               // -> 自己等自己 -> 永久死锁
```

所以仓库的正确做法是:**先 `RUnlock()` 彻底放掉读锁,再重新 `Lock()` 拿写锁**([async_job_registry.go:569](pkg/plugins/gateway/async_job_registry.go#L569) 的 `RUnlock` 和 [:575](pkg/plugins/gateway/async_job_registry.go#L575) 的 `Lock` 是分开的两段)。

> 代价:在 `RUnlock` 和 `Lock` 之间有一个「空窗期」,别的 goroutine 可能抢先删掉/修改同一条记录。这里能接受,是因为删一个已过期的 key 是**幂等**的(删两次等于删一次,无害)。但如果是「读到值后基于它做自增」这类操作,空窗期就会导致丢更新——那种场景要用别的办法(见 §3 atomic)。

### 2.5 底层原理

Go 源码 `src/sync/rwmutex.go` 里,`RWMutex` 结构体:

```go
type RWMutex struct {
	w           Mutex        // 写者之间仍用一把普通 Mutex 互斥
	writerSem   uint32       // 写者等「读者排空」的信号量
	readerSem   uint32       // 读者等「写者完成」的信号量
	readerCount atomic.Int32 // 当前持有读锁的读者数量(核心!)
	readerWait  atomic.Int32 // 写者在等的、尚未离开的读者数
}

const rwmutexMaxReaders = 1 << 30   // 读者数上限,约 10 亿
```

核心机制是 `readerCount` 这个原子计数器:

```
RLock():  readerCount 原子 +1   如果是正数 -> 直接获得读锁(无阻塞,超快)
RUnlock():readerCount 原子 -1

Lock()(写):
   1. 先拿内部的 w 这把 Mutex(保证同时只有一个写者)
   2. 把 readerCount 减去一个巨大的负数 (1<<30),
      这样后来的 RLock 看到 readerCount 是负数 -> 知道"有写者在等" -> 乖乖阻塞
   3. 等待此刻还在读的那几个读者全部 RUnlock 完毕
   4. 独占执行写操作
```

**图解说明**:精妙之处在于那个「减去 10 亿」的技巧。平时 `readerCount` 是正数(表示读者数)。写者一来,把它变成一个大负数,就同时完成了两件事:**(a) 告诉新来的读者「别进,有写者」**(读者看到负数就睡);**(b) 原来的正数部分 `readerCount + (1<<30)` 恰好算出「还有几个老读者没走,我要等几个」**。一个计数器,两个含义,这是 Go 标准库里很典型的位/数值技巧。

**选型建议(小白记这条就够)**:

- 读写差不多频繁、临界区极短 → 直接用 `Mutex`(RWMutex 自身有额外开销,未必划算)。
- 读 >> 写、且读临界区较长 → 用 `RWMutex`。

## 3. 进阶:锁 + `atomic` 做「无锁读」(仓库里的高级玩法)

这是本仓库里更漂亮的一个模式,看 [registry.go:29-33](pkg/utils/registry.go#L29-L33):

```go
type Registry[V any] struct {
	registry map[string]V
	values   atomic.Pointer[[]V] // 一份"不可变快照",读者无锁即可取
	mu       sync.RWMutex
}
```

它的设计思想(注释写在 [registry.go:26-28](pkg/utils/registry.go#L26-L28)):**读取缓存数组时,连读锁都不用加**。

看 `Array()` 方法 [registry.go:128-143](pkg/utils/registry.go#L128-L143):

```go
func (reg *Registry[V]) Array() (arr []V) {
	if cached := reg.values.Load(); cached != nil {   // ← 原子读,完全无锁!
		return *cached                                 //   直接返回快照
	}
	reg.mu.Lock()                                      // 只有缓存失效时才加锁重建
	defer reg.mu.Unlock()
	arr, _ = reg.updateArrayLocked()
	return arr
}
```

原理对比:

```
普通加锁读:          atomic 快照读:
  RLock()              Load()  (一条原子指令,几纳秒)
  读 slice             拿到一个只读快照,随便读
  RUnlock()            (读者之间零协调、零阻塞)
```

**图解说明**:关键前提是「**快照一旦发布就永不修改**」(immutable)。写者修改时,不去改老 slice,而是 **Copy-On-Write(写时复制)**:造一个新 slice,再用 `reg.values.Store(&updated)` 原子地「换指针」([registry.go:106-111](pkg/utils/registry.go#L106-L111))。老读者手上拿的还是旧快照,不受影响;新读者 `Load` 到的是新指针。因为读者永远不会看到「改了一半」的 slice,所以**读路径压根不需要锁**。

- `atomic.Pointer[T].Load()` / `.Store()`:对一个指针的原子读写,保证读者要么看到旧指针、要么看到新指针,绝不会看到「撕裂」的中间态。
- 写者仍然用 `mu.Lock()`([registry.go:92-96](pkg/utils/registry.go#L92-L96)),因为写者之间要互斥,且要同时改 `map` 和 `values` 两个字段,必须一致。

这个模式叫 **RCU 风格(Read-Copy-Update)**,适合「读极多、写极少、且能接受读者短暂读到旧值」的场景——正好是 Pod 列表这种缓存。你现在看懂思路即可,不用急着自己写。

## 4. `sync.Once`:只执行一次

还在同一个 Server 里,[async_job_registry.go:882-889](pkg/plugins/gateway/async_job_registry.go#L882-L889):

```go
func (s *Server) asyncJobRegistry() AsyncJobRegistry {
	s.asyncJobsOnce.Do(func() {          // 无论多少 goroutine 并发调用,
		if s.asyncJobs == nil {           // 里面这个函数全程只会执行一次
			s.asyncJobs = newAsyncJobRegistryForClient(s.redisClient, s.cache)
		}
	})
	return s.asyncJobs
}
```

`sync.Once` 解决「懒初始化(lazy init)」的并发安全:100 个 goroutine 同时第一次调用,`Do` 里的函数**保证只被执行一次**,其余 99 个会**阻塞等待那一次执行完**再往下走(确保它们拿到的是已初始化好的 `s.asyncJobs`,而不是 nil)。底层它用一个原子标志 + 一把内部 Mutex 实现,比你自己写「判断 nil → 加锁 → 再判断 nil(双重检查)」更简洁、更不容易错。

## 5. 小白必记的「踩坑清单」

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 复制含 Mutex 的结构体(方法用值接收者) | 锁状态被复制,互斥失效 | 一律用**指针接收者** `func (s *T)` |
| 忘了 `Unlock` / 某个 return 分支漏解锁 | 死锁 | 加锁后立刻 `defer Unlock()` |
| 持读锁时再去拿写锁(锁升级) | 立刻死锁 | 先 `RUnlock()` 再 `Lock()`(见 §2.4) |
| `RLock` 配 `Unlock`(写解锁)之类配错 | 行为未定义 | `RLock↔RUnlock`、`Lock↔Unlock` 严格配对 |
| 临界区里干重活(IO、网络、长循环) | 并发度暴跌,大家排队 | 临界区只做「改内存」,校验/IO 挪到锁外(见 [:556](pkg/plugins/gateway/async_job_registry.go#L556)) |
| 用锁保护一个计数器的 `x++` | 能用但偏重 | 这种单变量用 `atomic.Int64` 更快 |

**怎么自己验证有没有 data race?** Go 自带竞争检测器,仓库的 `make test-race-condition` 就是干这个的(见 AGENTS.md 的构建表)。平时你也可以:

```bash
go test -race ./pkg/plugins/gateway/...
```

它会在运行时插桩,一旦发现两个 goroutine 没加锁就并发读写同一地址,立刻报告是哪两行代码冲突——这是学并发时最好用的老师。

## 一句话总结

- **`Mutex`**:同一时刻只放一个进。零值可用、指针接收者、`defer Unlock`。
- **`RWMutex`**:读可并行、写独占;读多写少才划算;**不能把读锁升级成写锁**。
- **`atomic` + 不可变快照**:读路径彻底无锁的高阶优化(仓库 `Registry` 的做法)。
- **`sync.Once`**:并发安全的「只初始化一次」。

# claude - Goroutine:Go 并发的核心

## 0. 它是什么?和「线程」有什么区别?

goroutine 是 Go 自己管理的**超轻量级「执行单元」**。你可以把它理解成「一个能和别人同时跑的函数」。

和操作系统线程(OS thread)对比,这是小白最该先建立的直觉:

```
                操作系统线程              goroutine
初始栈大小        1 ~ 8 MB                约 2 KB(用多少涨多少,能缩)
创建成本          系统调用,较慢            几乎就是分配一小块内存,极快
能开多少          几千个就吃力             几十万、上百万很轻松
谁来调度          操作系统内核             Go 自己的运行时(runtime)调度器
切换成本          要陷入内核,较贵          用户态切换,很便宜
```

**图解说明**:一个 OS 线程光栈就要 1MB 起步,开一万个就是 10GB 内存,根本扛不住。
goroutine 初始栈才 2KB(Go 源码 `src/runtime/stack.go` 里的常量 `_StackMin = 2048`),而且栈是**按需增长、空闲时还能收缩**的。
所以 Go 程序里「每个请求开一个 goroutine」「每个后台任务开一个 goroutine」是完全正常、甚至推荐的做法——这在用线程的语言里是不敢想的。

## 1. 语法:就一个 `go` 关键字

```go
go f(x, y)          // 启动一个新 goroutine 去执行 f(x, y),当前代码不等它,立刻往下走
go func() {         // 更常见:启动一个匿名函数(闭包)
    // ... 这里的代码在新 goroutine 里跑 ...
}()                 // ← 注意结尾这个 () 是"调用",不能漏
```

三个你必须立刻记住的点:

1. **`go` 后面必须是一个「函数调用」**,不是函数定义。所以匿名函数结尾一定有 `()`。
2. **参数在 `go` 那一刻就求值了**。`go f(x)` 里的 `x`,是执行到这行时 `x` 的值被「拍下快照」传进去,后面主流程再改 `x` 不影响它。
3. **`go` 语句本身瞬间返回**,它**不返回任何值**。新 goroutine 的「结果」怎么拿回来?不能用返回值,只能靠 **channel(通道)** 或共享内存(配合锁)。这是小白最容易懵的地方——`go` 不是「调用并拿结果」,是「扔出去让它自己跑」。

## 2. 仓库真实例子①:用完即走(fire-and-forget)

看 [modelclaim_wake.go:64-84](pkg/plugins/gateway/modelclaim_wake.go#L64-L84) 这个「叫醒模型」的请求:

```go
func (r *runtimeModelWakeRequester) RequestWake(pod *v1.Pod, model string) bool {
	if r == nil || pod == nil || pod.Status.PodIP == "" || model == "" {
		return false
	}
	wakeKey := modelClaimWakeKey(pod, model)
	// 去重:同一个 (pod, model) 的唤醒正在跑,就不再重复发起
	if _, alreadyRunning := r.inFlight.LoadOrStore(wakeKey, struct{}{}); alreadyRunning {
		return false
	}
	operationID := wakeKey + "/" + uuid.NewString()
	go func() {                                     // ← 启动一个后台 goroutine
		defer r.inFlight.Delete(wakeKey)            //   跑完(无论成败)把去重标记删掉
		if err := r.wake(pod.Status.PodIP, model, operationID); err != nil {
			klog.ErrorS(err, "ModelClaim request-triggered wake failed", ...)
			return
		}
		klog.InfoS("ModelClaim request-triggered wake completed", ...)
	}()
	return true                                     // ← 不等 HTTP 完成,立刻返回 true
}
```

这是最典型的用法,为什么要这么设计?

```
调用方线程(处理一个用户请求)          新 goroutine(后台)
        |                                  
   RequestWake()                            
        |                                   
   go func{...}  ------ 派生 ------>   发 HTTP 去唤醒模型(可能耗时 2 分钟!)
        |                                   |
   return true (立刻!)                      | (调用方早就返回了,它还在慢慢发)
        |                                   |
   继续处理用户请求                          wake() 完成 -> defer 删除去重标记
```

**图解说明**:唤醒一个模型的 HTTP 调用最长可能 2 分钟(`modelClaimWakeTimeout`,[modelclaim_wake.go:38](pkg/plugins/gateway/modelclaim_wake.go#L38))。如果**不开 goroutine**,当前这个用户请求就得干等 2 分钟才能响应,完全不可接受。开了 goroutine,主流程「派发任务后立刻返回」,把慢活丢给后台慢慢干。

关键细节 `defer r.inFlight.Delete(wakeKey)`([modelclaim_wake.go:76](pkg/plugins/gateway/modelclaim_wake.go#L76)):这个 goroutine 无论成功还是报错,**它自己负责清理自己留下的去重标记**。goroutine 最好有「自扫门前雪」的习惯,否则就会泄漏状态。

> 这里还顺带用到了 `sync.Map`([modelclaim_wake.go:52](pkg/plugins/gateway/modelclaim_wake.go#L52))的 `LoadOrStore`——这是一个「检查+写入」的原子操作,保证并发的两个请求不会同时启动两个重复的唤醒。它是上一课讲的锁的「专用高配版」,适合这种「一写多读、key 相对稳定」的并发 map 场景。

## 3. ⚠️ 小白第一大坑:goroutine 不会「自动等你」

这是必须立刻理解的规则:**`main` 函数(主 goroutine)一旦返回,整个程序立刻退出,所有还没跑完的 goroutine 被无情杀死,不管它跑到哪了。**

```go
func main() {
    go func() {
        time.Sleep(time.Second)
        fmt.Println("我想打印这句")   // ❌ 大概率永远打印不出来!
    }()
    // main 到这里就 return 了 -> 程序退出 -> 上面那个 goroutine 还在 Sleep,被直接干掉
}
```

所以「怎么等 goroutine 们干完」是并发编程的核心问题之一。三种常见手段:

- **`sync.WaitGroup`**:等「一批 goroutine 全部干完」。
- **channel**:等「某个信号 / 某个结果」。
- **`context.Context`**:传递「取消 / 超时」信号(上面 `wake()` 里的 `context.WithTimeout` 就是,[modelclaim_wake.go:102](pkg/plugins/gateway/modelclaim_wake.go#L102))。

`WaitGroup` 的标准写法(仓库测试里到处都是这个模式):

```go
var wg sync.WaitGroup
for i := 0; i < 10; i++ {
    wg.Add(1)              // 计数 +1,必须在 go 之前加,不能在 goroutine 内部加
    go func() {
        defer wg.Done()    // 干完计数 -1(defer 保证一定执行)
        doWork()
    }()
}
wg.Wait()                  // 阻塞,直到计数归零(10 个全 Done 了)才往下走
```

心智模型:`Add` 往账上记数,每个 goroutine `Done` 还一笔,`Wait` 一直堵着直到账还清。**`Add` 一定要在 `go` 之前**,否则可能 `Wait` 先跑、发现计数是 0、直接放行,根本没等。

## 4. 仓库真实例子②:后台常驻 goroutine + 优雅退出

fire-and-forget 是「跑一次就没了」。另一种是「**一直跑,直到你叫它停**」——比如定时健康检查。看 [tokenizer_pool.go:475-489](pkg/plugins/gateway/algorithms/tokenizer_pool.go#L475-L489):

```go
func (p *TokenizerPool) startHealthChecker() {
	ticker := time.NewTicker(p.config.HealthCheckPeriod)  // 每隔一段时间触发一次
	go func() {
		defer ticker.Stop()                                // goroutine 退出时停掉 ticker,防泄漏
		for {                                              // 无限循环:后台常驻的标志
			select {                                       // 同时"监听"多个 channel
			case <-ticker.C:                               // 情况 A:定时器响了
				p.performHealthCheck()
				p.cleanupStaleTokenizers()
			case <-p.stopCh:                               // 情况 B:收到停止信号
				return                                     //   -> return,goroutine 结束
			}
		}
	}()
}
```

怎么叫它停?看 [tokenizer_pool.go:550-552](pkg/plugins/gateway/algorithms/tokenizer_pool.go#L550-L552) 的 `Close`:

```go
func (p *TokenizerPool) Close() error {
	close(p.stopCh)   // ← 关闭 channel,就是发出"停止"广播
	// ...
}
```

这是 Go 后台任务的**黄金模板**,一定要吃透:

```
          Close() 调用 close(stopCh)
                   |
                   v  (广播:所有 <-stopCh 立刻收到零值)
   +--------------------------------------------------+
   |  for {                                            |
   |    select {                                       |
   |      case <-ticker.C: 干活    <-- 平时走这条       |
   |      case <-stopCh:   return  <-- stopCh 一关走这条|
   |    }                                              |
   |  }                                                |
   +--------------------------------------------------+
                   |
                   v
            goroutine 干净退出,defer ticker.Stop() 执行
```

**图解说明**:

- **`for { select {...} }`** 是后台 goroutine 的标准骨架。`for` 让它循环不退;`select` 让它**同时等多个事件**,哪个先来处理哪个。
- **`select`** 像一个多路开关:它会阻塞,直到某个 `case` 的 channel 操作能进行。`ticker.C` 每隔 30 秒来一次数据,就走健康检查;而 `stopCh` 平时没动静(堵着),一旦被 `close`,`<-p.stopCh` 立刻返回,就走 `return`。
- **为什么用「关闭 channel」当停止信号,而不是发一个值?** 因为 `close(ch)` 是**广播**:哪怕有 100 个 goroutine 都在 `<-stopCh`,一次 `close` 能让它们**全部**同时收到信号。而往 channel 发一个值只能叫醒一个。所以「只读、永不发送、靠关闭来通知」是停止信号的惯用法——注意 `stopCh` 的类型是 `chan struct{}`([tokenizer_pool.go:67](pkg/plugins/gateway/algorithms/tokenizer_pool.go#L67)),`struct{}` 是「零大小」类型,表示「我只关心有没有信号,不关心内容」。
- **`defer ticker.Stop()`**([:478](pkg/plugins/gateway/algorithms/tokenizer_pool.go#L478)):goroutine 退出前把定时器资源释放掉。这叫**优雅退出(graceful shutdown)**——不是硬杀,而是让它自己收尾。

> 这一段还顺带和上一课的锁呼应:注意 `cleanupStaleTokenizers`([:516-547](pkg/plugins/gateway/algorithms/tokenizer_pool.go#L516-L547))里,**在锁内只收集要删的项、改 map**,把真正耗时的 `tok.Close()`(可能有网络 IO)挪到**锁外**执行。后台 goroutine 持锁时间越短,越不会拖住处理用户请求的那些 goroutine。

## 5. 底层原理:GMP 调度模型

小白不需要精通,但要有个图景,否则很多现象解释不了(比如「为什么我开了 10 万个 goroutine 电脑没炸」)。

Go runtime 用 **G-M-P** 三个角色调度(源码在 `src/runtime/proc.go`,核心结构体 `g` / `m` / `p`):

```
   G  = goroutine(你的任务,几十万个)
   M  = machine,即 OS 线程(真正能被 CPU 执行的,数量少)
   P  = processor,逻辑处理器(数量 = GOMAXPROCS,默认=CPU 核数)

        P0 (逻辑处理器)          P1
     +----------------+     +----------------+
     | 本地队列:       |     | 本地队列:       |
     | G3 G4 G5 ...    |     | G8 G9 ...       |
     +-------+--------+     +-------+--------+
             |                      |
          绑定 M0                 绑定 M1          <- M 是真线程,跑在 CPU 核上
             |                      |
          [CPU 核]               [CPU 核]

              全局队列: G100 G101 ...  (本地放不下时溢出到这)
```

**图解说明**:

- 成千上万个 **G** 排在队列里,但真正占用 CPU 的 **M(线程)只有少数几个**(约等于 CPU 核数)。runtime 的调度器不断地把队列里的 G 取出来、丢到空闲的 M 上去跑一小会,时间到了或 G 阻塞了,就换下一个。**这就是为什么几十万 goroutine 不会撑爆内存或拖垮系统**——它们绝大多数时间只是「在队列里排队的一小块内存」,不是真线程。
- **`GOMAXPROCS`** 决定同一时刻最多有几个 G 在**真正并行**地跑(默认等于 CPU 核数)。注意区分:**并发(concurrency)**是「同时有很多任务在推进」(逻辑上),**并行(parallelism)**是「同一物理时刻真有多个在跑」(需要多核)。goroutine 让你轻松写出高并发,到底多少并行由 `GOMAXPROCS` 和核数决定。
- **关键优势——遇到阻塞不浪费线程**:当一个 G 发起网络请求/读文件这类会阻塞的操作时,runtime 会把它从 M 上「摘下来」挂起,让这个 M 立刻去跑别的 G。所以上面 `wake()` 里那个 goroutine 等 HTTP 响应的 2 分钟里,它**没有占着任何线程空转**,线程被拿去干别的了。这就是 Go 高并发的秘密:**用极少的线程,承载极多的阻塞任务**。
- **work-stealing(工作窃取)**:P0 的队列空了,它会去 P1 的队列「偷」一半任务来跑,保证 CPU 不闲着、负载均衡。

## 6. ⚠️ 小白第二大坑:闭包捕获循环变量

这是面试必考、新手必踩的坑:

```go
// Go 1.22 之前的经典 bug
for _, pod := range pods {
    go func() {
        process(pod)   // ❌ 所有 goroutine 可能都处理了"最后一个 pod"
    }()
}
```

原因:1.22 之前,整个循环**共用同一个 `pod` 变量**,闭包捕获的是这个变量的「地址」而不是「当时的值」。等 goroutine 真正跑起来时,循环早就结束了,`pod` 停在最后一个,于是大家读到的都是最后一个。

两种修法(老代码里你会看到):

```go
// 修法 1:参数传值(就是前面说的"go 那一刻就求值")—— 最推荐,任何版本都对
for _, pod := range pods {
    go func(p *v1.Pod) {
        process(p)
    }(pod)                  // ← 把 pod 作为参数传进去
}

// 修法 2:循环内重新声明一个同名局部变量(著名的 pod := pod)
for _, pod := range pods {
    pod := pod              // ← 每轮创建一个新变量
    go func() { process(pod) }()
}
```

> **好消息**:**Go 1.22(2024 年初)起**,语言改了规则——每轮循环的循环变量都是**独立的新变量**,上面那个 bug 自动消失了。但你读老代码时还会大量看到 `pod := pod` 这种写法,得知道它是干嘛的;而且一旦捕获的不是循环变量而是别的可变状态,这个坑依然在,所以「`go func` 要用的外部变量,优先用参数传进去」始终是好习惯。

## 7. 小白必记的「踩坑清单」

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `main` 不等 goroutine 就返回 | goroutine 被直接杀死,活没干完 | 用 `WaitGroup` / channel / `ctx` 等它 |
| 后台 goroutine 没有退出机制 | **goroutine 泄漏**:程序开着它就永远在,越积越多 | 给个 `stopCh` 或 `ctx`,像 §4 那样能停 |
| 多个 goroutine 读写同一变量没加锁 | data race,数据错乱 / panic | 加锁(上一课)或用 channel 传递 |
| `go func(){...}()` 里直接用循环变量 | 1.22 前全指向最后一个值 | 参数传值 `go func(p){...}(pod)` |
| 往已关闭的 channel 发送 / 关闭两次 | **panic** | 只让「发送方」关 channel,且只关一次 |
| `WaitGroup.Add` 写在了 goroutine 内部 | `Wait` 可能提前放行 | `Add` 必须在 `go` 之前 |
| goroutine 里 panic 没 recover | **整个进程崩溃**(不只是这个 goroutine) | 后台 goroutine 入口加 `defer recover()` |

最后一条特别重要且反直觉:**一个 goroutine 里的 panic 如果没被 `recover`,会让整个程序崩溃**,不是只崩那一个 goroutine。所以长期运行的后台 goroutine,入口常加一层:

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            klog.Errorf("background goroutine panicked: %v", r)
        }
    }()
    // ... 实际工作 ...
}()
```

**怎么排查 goroutine 问题?**

```bash
# 竞争检测(和上一课一样,-race 是神器)
go test -race ./pkg/plugins/gateway/...
```

运行中的服务,还可以用 Go 自带的 `pprof` 看「此刻一共有多少 goroutine、它们都卡在哪一行」——goroutine 数量只涨不降,基本就是泄漏了。

## 一句话总结

- **`go f()`**:开一个超轻量执行单元,**立刻返回、不等它、不拿返回值**。
- **要结果 / 要等它**:用 `channel`、`sync.WaitGroup`、`context`,绝不用返回值。
- **用完即走**:慢活丢后台,主流程立刻返回(仓库 `RequestWake`)。
- **后台常驻**:`for { select { case <-事件: 干活; case <-stopCh: return } }` + `close(stopCh)` 优雅退出(仓库 `startHealthChecker` / `Close`)。
- **底层**:GMP 调度,少量线程(M)承载海量 goroutine(G),阻塞不占线程——这是 Go 高并发的根基。

要不要我接着帮你(1)**专门讲 channel**——它是 goroutine 之间通信的管道,`select`、带缓冲/无缓冲、`close` 的语义,配仓库里的 `stopCh`、队列代码精讲;还是(2)给你写一个**可运行的最小 demo**,用 `go run` 亲眼看到「不等 goroutine → 啥都没打印」「加了 WaitGroup → 全部打印」「闭包坑 → 全是最后一个」的对比?
