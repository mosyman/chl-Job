# Higress 背景

**Higress 是阿里巴巴开源的云原生 API 网关，技术底座是 Istio + Envoy，现在是 CNCF Sandbox 项目，最新定位是“AI 原生 API 网关”。** 它和你上一个问的 CloudWeGo 是互补关系：CloudWeGo（Kitex/Hertz）是微服务框架层，管服务间的东西向调用；Higress 是流量入口层，管南北向的流量治理。

## 诞生的原因：阿里的老网关遇到三个痛点

Higress 源于阿里内部对 Tengine（Nginx 衍生版）网关的不满，核心动机有三个：

1. **配置 reload 导致长连接中断**——Nginx 系网关改配置要重启 worker 进程，这对 WebSocket、gRPC、MQTT 这类长连接是致命的，而 Envoy 的热更新配置不会断连接；
2. **gRPC/Dubbo 负载均衡能力不足**——传统网关只能做四层/简单七层分发，无法感知 RPC 协议做精确负载均衡；
3. **网关割裂问题**——当时企业普遍要同时维护流量网关（如 Nginx）+ 微服务网关（如 Spring Cloud Gateway）+ 安全网关三套系统，Higress 的目标就是把三者合一。

阿里没有从零造轮子，而是基于社区 Istio + Envoy 做自研扩展，在内部经历了两年多、大规模生产验证后才开源。

## 发展历程

- **内部阶段**：先在阿里内部落地——优酷用它做南北向流量调度，钉钉用它做混合云流量调度，并探索了东西向流量分发和三类网关的融合；
- **2022 年 11 月**：在云栖大会正式开源（最初仓库在 alibaba/higress 下，现迁移到 [higress-group/higress](https://github.com/higress-group/higress)）；
- **之后进入 CNCF Sandbox**，成为沙箱项目；
- **2024 年起转型 AI 网关**：随着大模型爆发，Higress 成了通义千问 APP、百炼大模型 API 的支撑网关，官方定位也升级为 "AI Native API Gateway"。

## 现在的样子：两大能力面

**云原生网关面**（老本行）：Ingress、服务发现对接 Nacos/Zookeeper/Consul 等多注册中心、协议转换（HTTP→Dubbo/gRPC）、认证鉴权、WAF、限流，插件支持 Go/Rust/JS 编写的 Wasm 热插拔。

**AI 网关面**（新主线）：统一接入 100+ 大模型（OpenAI 协议转换）、Token 级限流和消费者额度管理、语义缓存、提示词攻击检测等内容安全能力，以及 [MCP Server 托管](https://higress.ai/docs/ai/mcp-server)——把传统 API 转成 MCP 工具对外发布，相当于建一个私有 MCP 市场。这也是目前社区最活跃的方向。

## 学习/选型建议

结合你之前在了解 CloudWeGo：如果走字节系微服务技术栈，典型的组合就是 **Higress 做入口网关 + Kitex/Hertz 做内部服务**。学 Higress 的话，前置知识是 Envoy/Istio 的基本概念（xDS、数据面/控制面分离），入门材料首推[官方博客的开源介绍文](https://higress.ai/blog/higress)和[官方 FAQ](https://higress.ai/docs/latest/overview/faq)；想做 AI 方向，直接从 AI 网关文档和 MCP 插件入手即可。
