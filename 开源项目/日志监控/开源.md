## 阿里巴巴

| 项目 | 定位 | 说明 |
|---|---|---|
| **LoongCollector**（原 iLogtail） | 日志/可观测数据采集器 | 最值得关注的那个：阿里云 SLS 团队开源，Go 编写，CNCF Sandbox 项目。阿里内部日处理数十 PB，可采文件、容器输出、指标、Trace，插件化架构，对标 Filebeat/Fluentd 但性能更强 |
| **KubeSkoop** | K8s 网络监控 | 专注容器网络（丢包、RTT、连接异常）的定位诊断工具，Go 编写 |
| **Sentinel Go** | 流控/熔断 | 严格说是流量治理而非监控，但提供实时指标统计，常和监控配合用 |

## 字节跳动

| 项目 | 定位 | 说明 |
|---|---|---|
| **CozeLoop** | AI 应用可观测平台 | coze-dev 组织开源，提供链路追踪、指标监控（延迟/Token 消耗/错误率）、日志聚合；和 CloudWeGo 的 Eino 通过 Callback 机制官方打通，做 AI 应用观测正好 |
| **Elkeid** | 主机安全与监控 | 字节的 HIDS 主机入侵检测系统，包含主机上的进程/网络监控能力，Go + Rust |
| **obs-opentelemetry**（kitex-contrib / hertz-contrib） | 框架级 OTel 集成 | 给 Kitex/Hertz 一行代码接入 OpenTelemetry 链路追踪和指标，学 CloudWeGo 必看 |
| **Kelemetry**（kubewharf 组织） | K8s 控制面观测 | 字节 kubewharf 项目群的一员，做 K8s 对象的全局审计和事件链路追踪，Go |

## 其他大厂（顺带推荐）

- **Nightingale 夜莺**（滴滴开源、现由快猫星云维护）：Go 编写的监控告警平台，可以理解为 Prometheus 的企业级上层，国内社区非常活跃；
- **DeepFlow**（云杉网络）：eBPF 零侵扰可观测性，Go 编写，CNCF Sandbox，自动给 Go/Java 等服务生成调用链，不需要改代码；
- **Open-Falcon**（小米）：Go 监控系统鼻祖，现在偏老，了解即可；
- **Apache SkyWalking**（华为背景）：后端 Java 但有官方 Go Agent，APM 领域 Apache 顶级项目。

## 怎么选

如果目的是**给自己的 Go 服务加日志和监控**，优先走社区标准路线：OpenTelemetry-Go（指标+链路）+ Prometheus + Loki/Vector，再用上面大厂项目补短板——比如需要高性能日志采集就上 LoongCollector，做 AI 应用就用 Eino + CozeLoop，容器网络排障用 KubeSkoop。如果目的是**读源码学习**，LoongCollector 的插件化管道设计和 DeepFlow 的 eBPF 实现是含金量最高的两个。

# obs-opentelemetry：CloudWeGo 生态的官方 OTel 扩展

**它是 Kitex/Hertz 官方维护的 OpenTelemetry 接入扩展，让框架一行配置就获得分布式链路追踪、指标上报和日志关联能力。** 它们不在主框架仓库里，而是放在 CloudWeGo 的两个扩展组织中：

- Kitex 的：**[github.com/kitex-contrib/obs-opentelemetry](https://github.com/kitex-contrib/obs-opentelemetry)**
- Hertz 的：**[github.com/hertz-contrib/obs-opentelemetry](https://github.com/hertz-contrib/obs-opentelemetry)**

这两个 contrib 组织就是之前提过的 CloudWeGo 生态配套仓库，除 OTel 外还托管注册中心、监控等几十个扩展。

## 它具体做了什么

1. **自动埋点**：服务端收到请求、客户端发起调用时自动创建 Span，并把 trace context 通过 RPC 元数据透传给下游——这样一次请求跨 N 个微服务的完整调用链能串起来；
2. **指标采集**：按 RPC 维度产出 QPS、延迟、错误率等 metrics；
3. **日志关联**：`logging` 子包提供 zap/logrus 的 provider，能把 trace_id、span_id 注入日志字段，实现“日志 ↔ 链路”互相跳转；
4. **可插拔后端**：数据通过 exporter 输出，支持 stdout（调试）、OTLP、Jaeger 等，后端随你选。

## 用法示例

**Kitex 侧**（先初始化 exporter provider，再传入框架 Option）：

```go
import (
    "github.com/kitex-contrib/obs-opentelemetry/provider"
    otelkitex "github.com/kitex-contrib/obs-opentelemetry/tracing"
)

svr := echo.NewServer(new(EchoImpl), otelkitex.NewDefaultServerOption())
// 客户端侧对应 otelkitex.NewDefaultClientOption()
```

**Hertz 侧**（是标准的中间件形式）：

```go
import (
    "github.com/hertz-contrib/obs-opentelemetry/provider"
    otelhertz "github.com/hertz-contrib/obs-opentelemetry/tracing"
)

p := provider.New(provider.WithServiceName("your-service"))
defer p.Shutdown(ctx)

h := server.Default(server.WithTracing(otelhertz.NewServerTrace()))
```

（具体 API 随版本可能有差异，以官方文档和示例为准。）

## 为什么值得学

OpenTelemetry 是 CNCF 的可观测性事实标准。你的服务接了这套扩展后，数据可以对接任意标准后端——自建的 Jaeger + VictoriaMetrics/Prometheus，或者商业产品（阿里云 ARMS、火山引擎 APMPlus 都有官方对接文档）。这也是字节内部做法的开源版：框架层只管产生标准数据，存储和展示解耦。

学习材料直接看三样：[Kitex 可观测性文档](https://www.cloudwego.io/docs/kitex/tutorials/observability/tracing)、[Hertz OpenTelemetry 教程](https://www.cloudwego.io/docs/hertz/tutorials/third-party/open-telemetry)，以及 [hertz-examples/opentelemetry](https://github.com/cloudwego/hertz-examples/blob/main/opentelemetry/README.md)——这个示例仓库自带 docker-compose，能一键拉起 OpenTelemetry Collector + Jaeger + VictoriaMetrics 全套后端，本地跑通一条完整链路，是最快的上手方式。
